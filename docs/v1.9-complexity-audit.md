# WMP v1.9 复杂度审计报告（终版 · 已裁决）

> 目标：在"稳定可用"最高优先级下，逐项审查系统中"非必需复杂度"机制，给出删除影响与保留理由。
> 审计日期：2026-10-30 ｜ 基线版本：v1.8.0（含幂等键 hotfix e6c138a）
>
> **最终结论：零代码改动。** 审计确认现有复杂度均系业务刚需（幂等键防副作用链重复、乐观锁+行锁保状态机合法、附件分片支撑 >64MB 大文件），无安全可砍项。v1.9 成果为开发规范固化（见第五节）与两项备查登记。
>
> 关键背景：用户确认附件可能超过 50MB（邮件系统普遍限 25–50MB，大文件恰需平台承载），故附件分片上传链路**保留**，审计中"建议删除"的初步方案作废。

## 裁决图例

- ✅ **保留**：机制在正确使用，删除代价大于收益
- 🔧 **简化**：机制方向对，但实现可以砍掉一部分
- ❌ **建议删除**：复杂度明显超过当前收益
- ❓ **待裁决**：需要业务输入才能决定

## 一、后端机制

### 1. 幂等键（`creation_key` + `creation_hash`）— 🔧 建议保留，见裁决点 R1

| 维度 | 说明 |
|---|---|
| 是什么 | 创建 WKD 时按"请求内容 SHA-256"生成幂等键；网络重试命中同键直接返回首次结果，不同内容复用同键返回 409 |
| 复杂度来源 | 概念心智成本 + 唯一索引 + 2 项契约测试 |
| 故障史 | **v1.7 用固定 UUID 当键 → 演示事故 409**；v1.8 改为内容哈希后修复 |
| 删除影响 | 网络重试 / 双击 / 刷新重提会产生重复 WKD，且编号序列、附件绑定、审计历史全部变脏，事后无低成本清理手段 |
| 更简替代 | 前端 loading 锁 + 按钮置灰，只能挡住"同一窗口的误操作"，挡不住网络重试；DB 唯一约束只能事后报错，不能合并请求 |

**结论**：WKD 创建是副作用链操作（编号、附件绑定、审计），不是简单插行。当前实现已修复并有测试，维护成本低。**建议保留。**

### 2. 乐观锁 `lock_version`（状态流转强制）— ✅ 保留

| 维度 | 说明 |
|---|---|
| 是什么 | 所有状态流转接口强制校验 `lock_version`，版本不符返回 409，要求用户刷新 |
| 复杂度来源 | 前端必须在每次提交时回传最新版本（草稿逻辑已处理） |
| 故障史 | 无 |
| 删除影响 | 两人同时操作同一 WKD 时，后提交者静默覆盖前者，状态机可能非法跃迁 |

**结论**：这是比数据库行锁更稳的并发控制（冲突早发现、不依赖方言细节），且已在实际使用。**保留。**

### 3. 悲观行锁 `with_for_update(of=...)` — ✅ 保留，但立规范

| 维度 | 说明 |
|---|---|
| 是什么 | 2 处：状态流转锁 Wkd 主表、附件绑定锁 Attachment 主表 |
| 故障史 | **v1.8 前未加 `of=`，SQLAlchemy `lazy='joined'` 产生 outer join，PG 直接报错**；修复为 `of=Wkd` 后正常 |
| 删除影响 | 并发流转同一 WKD 可能产生双份历史记录或非法状态 |

**结论**：保留。**v1.9 开发规范新增一条：项目内一律使用 `with_for_update(of=<主表>)`，禁止裸 `with_for_update=True`。**

### 4. 上传会话 + 多模分片上传（`UploadSession` / multipart）— ✅ 保留（已裁决）

| 维度 | 说明 |
|---|---|
| 是什么 | 附件先创建"上传会话"→ 预签名 URL 直传 RustFS → 完成回调 → 绑定 WKD。>64MB 文件走 S3 multipart 分片（16MB/片），配套：过期会话清理后台任务、PG advisory lock 防多实例双跑、孤儿分片 abort |
| 复杂度来源 | 上传会话状态机（OPEN/EXPIRED）、附件状态机（UPLOADING/READY）、后台清理循环、advisory lock、分片 abort、前端分片上传 + 指数退避重试。后端 224 行 + storage 71 行 + 前端约 100 行 |
| 裁决理由 | **业务确认附件可能超过 50MB**（邮件系统普遍限 25–50MB，大文件恰需本平台承载）。删除分片分支等于大文件直接传失败，才是真正的稳定性问题。**保留，分片阈值 64MB 不动。** |

### 4.1 重要澄清：两套文件存储链路相互独立

| | 原子操作文件（UPLOAD_FILE） | WKD 附件（attachments） |
|---|---|---|
| 存储位置 | DB，`wkd_operations.params.files[].content`（base64 内嵌） | RustFS 对象存储，DB 仅存元数据 |
| 一致性 | 随 WKD 同事务落库，天然无孤儿 | 上传会话 + 完成回调绑定 |
| 上限 | 总量 100MB（原始大小） | 单文件 500MB，>64MB 走分片 |
| 选择理由 | 小脚本/配置文件，要求与 WKD 同生共死 | 大佐证材料，不能胀数据库 |

**双轨是刻意的**：要事务的进 DB（小），要容量的进对象存储（大），不用一套方案硬套两种场景。

### 5. lifespan 手写 DDL（无 Alembic）— 🔧 简化管理，不引入 Alembic

| 维度 | 说明 |
|---|---|
| 是什么 | 启动时 `create_all` + 一串幂等 `ALTER TABLE ... IF NOT EXISTS` 补列 |
| 风险 | 启动即跑 DDL，SQL 写错服务直接起不来；无版本表、无回滚 |
| 替代 | 引入 Alembic 是行业标准，但为内网单系统引入一套迁移工具 + 运维命令，复杂度收益比一般 |

**结论**：保留现状，但 v1.9 起加规则：**schema 变更须出单独 SQL 脚本由部署方评审后手工执行，禁止再往 lifespan 里加 ALTER；存量 ALTER 冻结不再扩。**

### 6. OAuth 登录 + 首次登录自动注册 + 占位项目 — ✅ 保留

业务刚需，无简化空间。

### 7. RustFS 对象存储 — ✅ 保留

附件放 DB（大字段）或服务器本地盘都比对象存储更差，此项是正确选型。

### 8. 配置 `lru_cache`、Pydantic 入参校验、角色鉴权装饰器 — ✅ 保留

零故障记录，是框架级标准用法，不是自造复杂度。

## 三、裁决结果汇总（终版 · 2026-10-30 用户裁决）

| 编号 | 裁决项 | 结果 |
|---|---|---|
| R1 | 幂等键去留 | **保留**（已修、有测试、删除代价大） |
| R2 | 附件分片上传链路去留 | **保留**——业务确认附件可能超过 50MB；邮件系统普遍限 25–50MB，大文件恰需本平台承载，删除分片等于大文件传失败 |
| R3 | lifespan DDL 冻结 | **同意冻结**——不引入 Alembic，schema 变更改出独立 SQL 脚本由部署方评审执行，禁止再往启动流程加 ALTER |

**v1.9 零代码改动。** 审计确认：现有复杂度均被业务刚需钉死，没有可以安全砍掉的大块。复杂度事故的主要教训是 v1.7 幂等键误实现（已随 v1.8 hotfix e6c138a 修复），防复发靠规范而非删码。

## 四、v1.9 起生效的开发规范（防复杂度再生）

1. `with_for_update` 一律带 `of=<主表>`，禁止裸 `with_for_update=True`；
2. 新增 schema 变更必须出独立 SQL 脚本经评审后手工执行，lifespan 内 DDL 冻结；
3. 引入任何非平凡机制前，必须书面给出失败模式分析 + 对应测试，做不到就不引入；
4. 展示值与存储值分离的枚举（如机台状态），前后端必须以英文枚举值传输，中文仅作展示；
5. 默认用最笨但最可靠的技术（唯一约束、事务、前端 loading 锁），只有当笨办法解决不了才升级方案。

## 五、低风险备查登记（不影响运行，仅备查）

1. `schemas.py:151` 幂等键 pattern `^[A-Za-z0-9_-]{8,64}$` 与内容哈希生成规则耦合，改哈希算法时需同步——已有契约测试兜底。
2. 清理任务的 advisory lock 硬编码锁号 `827364501`，若未来多服务共用同一 PG 实例需注意冲突（概率极低，登记备查）。
